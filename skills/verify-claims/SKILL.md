# Verification Discipline（验证纪律）

目标：**没有证据，不得声称完成**。这个 skill 约束"收尾发言"，不负责实现。

## 何时使用

- 准备说「做完了 / 修好了 / 测试通过 / 可以合并 / 可以发布」之前；
- 每轮开发结束、写执行回执之前；
- 验收确认、代码复核、部署发布之前。

## 证据分级（至少满足一条，且必须能落盘/复现）

| 主张 | 必需证据 | 反例（不算证据） |
|---|---|---|
| 功能已实现 | 验收条目 + 截图/差异图（或测试报告） | 只贴代码、只写"已完成" |
| Bug 已修复 | 复现步骤 + 修复前/后输出，或回归测试通过 | "应该好了"、"看起来没问题" |
| 测试通过 | 测试命令 + 输出（通过/失败数）+ 命令可复现 | 只写"测试通过"、截图里没有命令 |
| 构建通过 | 构建命令 + 产物路径/退出码 | 只写"构建成功" |
| 部署完成 | 发布清单（版本/产物/URL/回滚）+ 可访问性检查 | 只写"已部署" |
| 代码可合并 | 审核账本 blocking=0 | 只看 diff 就下结论 |

## 强制规则

1. **先跑后说**：声称前必须实际执行命令/打开页面/读报告；输出原文（可截断，但要保留退出码与关键行）。
2. **失败要如实**：失败就给原始错误 + 定位；不要用"环境问题"掩盖。
3. **不能复现就写"未验证"**：写明缺什么、下一步怎么补，禁止把它当成通过。
4. **证据要落盘**：测试报告 → `test-report.json`；截图 → `evidence.shots`（项目内路径）；审核 → ledger。回执里 `used_skill_or_mcp: "verify-claims"`，`artifacts` 指向证据。
5. **不采信自述**：实现者的总结、注释、PRD 的"已完成"都只是线索，以真实输出为准。
6. **一条主张一条证据**：不要把"测试通过"当成"实现正确"的证据，也不要把"截图能打开"当成"功能正确"。

## 输出格式（写进回执/汇报）

```
结论：<完成 | 部分完成 | 未完成>
证据：<命令/报告/截图路径 + 关键输出行>
未覆盖：<没有验证的部分，或"无">
下一步：<需要补的验证动作，或"无">
```

## 与驾驶舱的集成

- 回执必须带 `used_skill_or_mcp: "verify-claims"` 与 `artifacts`（证据路径）；
- 测试阶段的技术门校验 `test-report.json`（命令/通过/失败/时间）；
- 验收阶段的技术门校验 `acceptance.json` 的证据真实存在；视觉变化会触发 stale（需重新确认）。

## 严禁

- 声称"完成/修复/通过"但没有任何输出或报告；
- 把"没有报错"当成证据；
- 把失败说成"部分成功"而不写失败项；
- 用截图代替可复现命令（截图只能作为补充证据）。
