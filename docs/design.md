# 项目驾驶舱 · 功能设计

> 2026-11-20 · 完整功能设计（产品视角）
> 插件：`@hunyed15/project-cockpit`

## 1. 一句话

**把项目真实状态收拢成一屏，让人一眼知道：做到哪了、卡在哪、谁在干、下一步做什么。**

它不生产业务数据，也不另存状态；它读已有工具产出的事实，归一、投射、并给出唯一动作。

## 2. 谁在用、什么时候用

**范围先定死**：这是 DeepSeek Harness 的插件，只管 DSH 内部，不接外部 agent。

- **项目 = 工作区（workspace）**。DSH 每新建一个工作区，插件里就该有它的一条项目信息——**哪怕是空目录**，也要以「未初始化」的形态出现，并给出"初始化 trellis"的下一步。
- 一个工作区里可能有多个会话（单线开发 1 个，多 agent 并行 N 个），会话是执行单元，项目是归属单元。

用户画像：非技术创始人 / 独立开发者，多项目，以 AI 为主要开发者。

每天打开 DSH 时问的问题：

| # | 问题 | 对应界面 |
|---|---|---|
| 1 | 我有哪些项目、各自到哪了？ | 项目总览（= 工作区列表） |
| 2 | 这个项目做到哪了？ | 生命周期 + 三本账 |
| 3 | 卡在哪？ | 三本账（缺陷）+ 下一步 |
| 4 | 下一步做什么？ | 下一步 |
| 5 | 谁在干、会不会撞？ | 并行 |

## 3. 设计原则

1. **不生产数据，只归一与投射。** 功能来自 trellis 任务，缺陷来自审核账本，会话来自宿主服务。加一个数据源 = 加一个适配器，不改视图。
2. **视图层不认识数据源。** 视图只认四类事实（功能 / 缺陷 / 阶段门 / 会话），永远不知道哪个文件、哪个插件产的。
3. **不给"看起来合理"的数字。** 读不到就显示 `—` 或"待确认"，绝不默认 0、不猜状态、不解析自由文本算进度。
4. **一步一个动作。** 主按钮只有一个；需要人决策的事交回对话，不在面板里发明快捷通道。
5. **同一屏口径一致。** 数据不可信时，chip、下一步、阶段门、表格一起降级，不能一半说"无问题"一半说"可能偏低"。

## 4. 信息架构：两级

**第一级 · 项目总览（= 工作区列表）**

每个已登记工作区一行，空目录也在列：

```
项目                 阶段       待修  在跑   更新于
claude-code-review   挑毛病      3    2     14:40
SuJinCRM             写代码      0    1     09:12
临时会话             未初始化     —    —      —
```

- 空目录/未初始化工作区不隐藏，状态列直接写「未初始化」，点进去给"初始化 trellis"的下一步。
- 每行可点进第二级。

**第二级 · 单项目详情**

```
┌───────────────────────────────────────────────────────────────┐
│ 项目名 · [待修 3 / 无待修 / 待确认] · 更新于 · 刷新 · ← 返回     │  ← 数据可信度
├───────────────────────────────────────────────────────────────┤
│ 异常横幅（仅在有数据问题时出现，可重试）                        │
├───────────────────────────────────────────────────────────────┤
│ 下一步：修复并复检                                             │
│   指令原文（标识符等宽）  ← 可直接粘贴执行                      │
│   理由 · 上次发送                      [去对话发送][复制][摘要] │
├───────────────────────────────────────────────────────────────┤
│ 生命周期：想清楚→定规格→搭骨架→写代码→挑毛病→验效果→发出去       │
├───────────────────────────────────────────────────────────────┤
│ 三本账：功能（= 任务） / 未归属缺陷                              │
├───────────────────────────────────────────────────────────────┤
│ 并行：N 个在跑 / 共 M 个会话 · 撞车预警                          │
└───────────────────────────────────────────────────────────────┘
```

## 5. 各区功能

### 5.1 数据可信度（顶部 + 横幅）

- **三态 chip**：`待修 N`（有阻塞）/ `无待修问题`（读到了且干净）/ `状态待确认`（数据不完整——账本异常或读取失败）。
- **异常横幅**：列出最多 3 条原因 + 剩余条数；带「重试」。
- **降级是整屏的**：一旦进入"待确认"，下一步改「先确认数据」并禁用主按钮，阶段门改「待确认」，表格缺陷列显示 `—`。

### 5.2 下一步

三层结构，缺一不可：

| 层 | 内容 | 作用 |
|---|---|---|
| 动作名 | 人话（修复并复检 / 复检本轮修复 / 跑第一次审核 / 跑提交门禁 / 初始化） | 做什么 |
| 指令原文 | 可直接执行的文本，标识符等宽 | 怎么做 |
| 理由 | 为什么是它 | 可反驳 |

状态机（优先级从高到低）：

| 条件 | 动作 |
|---|---|
| 项目未初始化 | 初始化 trellis |
| 有未处置 blocking | 修复并复检 |
| 有已标记 fixed 待复检 | 用 range 复检 |
| 从未审核 | 跑第一次 full |
| 全绿 | 跑提交门禁 |

### 5.3 生命周期（七阶段）

| 阶段 | 判据（推断） |
|---|---|
| 想清楚 | spec 文件数 > 0（近似，文案必须标"近似"） |
| 定规格 | `.trellis/spec/**` 文件数 |
| 搭骨架 | 项目已初始化 |
| 写代码 | 存在 in_progress / completed 任务 |
| 挑毛病 | 有审核轮次 **且无未处置 blocking** |
| 验效果 | 第二版接入（恒未完成） |
| 发出去 | 第二版接入（恒未完成） |

- 展示：一条 7 段进度线 + 当前门一句话 + 依据；明细默认收起。
- 「第二版接入」的门用**虚线**，与"没做"的实心浅灰区分。
- 当前门只能有一个；每道门必须有 `basis`。

### 5.4 三本账

**功能账**（= trellis 任务，已定：任务即功能）

| 列 | 来源 |
|---|---|
| 功能名 | `task.title` |
| 状态 | `task.status` → 进行中 / 已完成 / 未开始 |
| 作用域 | `task.relatedFiles`（缺失则 `—`） |
| 待修 | 归属到该功能的未处置 blocking 数 |
| 最近轮次 | 该功能账本的最后轮次 + verdict |

> 粒度说明：一个 trellis 任务就是一个功能，代价是粒度偏粗（一个大任务算一个功能），收益是**零新增写作约定**——现有 `task.json` 直接可用。将来真需要更细时，再在 `task.json` 里引入 `features[]` 数组，届时只改适配器。

**缺陷账**

- 每个功能的缺陷数来自审核账本（口径：`failOn` 取报告 `meta.failOn`，缺失回退 `critical/important`；处置必须轮次匹配）。
- 点击/展开可看最多 3 条：严重度 + 标题 + `文件:行`。
- **归属规则**：`issue.file` 按路径前缀匹配 `task.relatedFiles`。匹配不上的进「未归属」单列——如实显示，不硬塞。
- **允许手工指派**（已定）：未归属缺陷可以把「功能」指派给人选的任务。指派写在本插件的自有状态里（`.dsh/plugin-state/`，trellis 不托管），**不修改审核账本**；每条指派可撤销，撤销后回到「未归属」。手工指派在界面上标「人工指派」，与自动匹配区分开。

**门禁账**

- 最近一次 gate 的结果与快照一致性（复用审核插件的账本语义）。
- 截断的 full pass 不算通过。

### 5.5 并行

| 列 | 来源 |
|---|---|
| 会话 | `sessionQuery.readTitleSnapshots`；子代理标层级 |
| 目录 | `SessionHeader.cwd` 与项目根比对 → 主工作区 / 其他目录 |
| 状态 | `ctx.sessions.list()`（内存态最权威） |
| 创建于 | `SessionHeader.createdAt` |

- **范围**：`cwd` 在项目根下，或父会话在项目根下（worktree 会话属于后者）。
- **撞车预警**：两个"运行中"的会话在同一目录 → 横幅点名（同目录并行必然互相覆盖）。
- **worktree 不跑 git 判定**，界面说"其他目录"，不假装能识别 worktree。
- 上限 20 行，超出提示"只列出最近 N 个"。

## 6. 四类事实与数据源

| 事实 | 来源 | 关键字段 | 缺失时 |
|---|---|---|---|
| feature | `.trellis/tasks/*/task.json` | `title / status / subtasks / relatedFiles` | 任务表为空，显示"未初始化" |
| defect | `<task>/review/review-N.json`、`dispositions.jsonl` | `review.issues[].severity/file/line/key/issue`、`meta.failOn`、`meta.round` | 缺陷列 `—`，不显示绿 0 |
| gate | 上面两者 + `.trellis/spec/**` | 文件数、任务状态、轮次数 | 整屏「待确认」 |
| session | `sessionQuery.listSessions()` + `ctx.sessions.list()` | `header.cwd / parentSession / origin / delegationDepth / createdAt` | 并行区显示原因，其余不受影响 |

## 7. 架构分层

```
适配器层   trellis · 审核账本 · sessions ·（将来）任务板 / 验收结果 / 外部插件
             每个源：{ id, read(), 版本假设, 降级文案 }
   ↓ 只读、可选、互不依赖；一个源坏了只影响它自己
归一化层   四类事实（纯函数，可单测）
   ↓
视图层     五区（只认归一化事实）
   ↓
行动层     唯一动作 + 两步发送
```

**硬约束**：视图层不得 import 任何适配器；新增数据源只允许新增适配器。

### 7.1 整机分工：谁是发动机

用一辆车来分，避免"插件把流程自己跑一遍"这个最常见的错位：

| 车的部件 | 在本系统里是什么 | 归属 |
|---|---|---|
| **发动机** | LLM agent loop：理解目标、选工具、纠错、收尾 | DSH 内核，**插件不碰** |
| **底盘** | Host 服务：会话、工具、worktree、存储 | DSH 内核 |
| **轮子** | skills / 工具：trellis、审核、todos、前端/测试技能、playwright… | 各自插件或项目 |
| **变速箱 / 传动** | 派活通道：把一句指令送进目标会话（现为两步发送） | 插件实现，但不改语义 |
| **差速器 / 多轮驱动** | subagent：同一目标下的并行执行单元 | DSH 内核 + 派活 |
| **仪表盘 + 方向盘** | 本插件：显示状态、指出唯一动作、按一下派活 | **本插件** |

关键一句：**插件不是发动机**。它若自己按顺序调用技能、自己判断"下一步做完了没有"，就等于重造 agent loop——那正是"造轮子"的陷阱。

正确的闭环（驱动权始终在 agent）：

```
读状态（四类事实） → 算出唯一下一步 → 把这一句派给会话
        ↑                                      ↓
   结果写回账本  ←────────  会话里的 agent 执行（选技能、改代码、跑审核）
```

### 7.2 subagent 怎么参与

- subagent 是**执行单元**，不是新的驱动者：主会话（Lead）决定"做什么"，subagent 只执行被派的那一段。
- 并行度由**写作用域**约束（每个 subagent 一个 worktree + 一个 `write_scopes`），不靠"大家小心点"。
- 插件对 subagent 只做两件事：**看见**（并行区：谁在跑、在哪个目录）与**派活**（把任务文本送进指定会话）。插件不负责启动/回收 subagent——那是 agent 的 `subagent` 工具与 DSH 内核的事。

### 7.3 借鉴 `dsh-superagent` 的结构（不引依赖）

DeepSeek 开源的 [`dsh-superagent-prototype`](https://github.com/deepseek-ai/dsh-superagent-prototype) 是同一类问题的官方参考实现。它可复用的不是代码，是三个结构：

| 它做的 | 对我们的意义 |
|---|---|
| **Main Session（编排）vs Executor Session（干活）**，一个工单一个会话 + 一个目录 | 正好是"Lead / Teammate"的分工，也是"多轮驱动"的标准形态 |
| **工单状态独立于会话状态**（Ticket 自己 maintain `open → ended`） | 面板状态不能绑在"会话还开着没有"上，否则一关会话就丢进度 |
| **结构化 Report 状态**：`progress / waiting / ready / blocked / failed / dropped`，其中 `waiting` 必须由**结构化字段**声明，并明确拒绝"从报告自由文本推断在等人" | 直接印证我们的原则：**"需要人介入"必须是结构化事实，不能猜**。面板的"待人工决定"只能来自这种字段 |

它把「从自由文本推断 waiting on a person」明确列为 rejected concept——这条我们照抄：面板永远不会根据一段话推测"这是不是要人决策"。

## 8. 行动层

- 面板是 root scope，拿不到会话输入能力，因此**两步**：点击 → 跳回对话，输入框上方通栏确认 → 走用户自己的发送通道。
- 通栏三键：`填入输入框`（主）/ `发送` / `忽略`；两者都会替换草稿，必须明示。
- 记「上次发送」时间（本地），区分"还没做"与"刚做完、账本未更新"。
- 将来的动作（同一条通道，不新增特权）：`催一下`（向指定会话 steer）、`开始集成`（发给集成会话）。

## 9. 降级矩阵

| 缺失/异常 | 可信度区 | 下一步 | 生命周期 | 三本账 | 并行 |
|---|---|---|---|---|---|
| 无 `.trellis` | 待确认 | 初始化 | 首门未完成 | 空态 | 正常 |
| 账本坏行 | 待确认 + 原因 | 先确认数据（禁用） | 待确认 | 缺陷列 `—` | 正常 |
| 读取失败（HTTP/超时） | 待确认 + 旧数据时间 + 重试 | 先确认数据（禁用） | 待确认 | 保留旧数据并标时间 | 正常 |
| 无 `sessionQuery` | 不受影响 | 不受影响 | 不受影响 | 不受影响 | 显示原因 |

## 10. 非目标

- 不重造待办（dsh-todos 之类）、不做甘特图、不做趋势图/热力图
- 不写项目里任何文件；要存只存 `.dsh/plugin-state/`
- 不解析 PRD 文本算完成度、不跑 git 判定 worktree、不给"看起来像"的数字
- 不做多项目并列看板（跨项目字段预留，不实现）

## 11. 里程碑与验收

| 步 | 内容 | 验收标准 |
|---|---|---|
| **M1** | 项目总览（= 工作区列表，空目录也在列） | 每新建一个工作区就出现一行；空目录/未初始化显示「未初始化」且下一步是"初始化 trellis"；点行进入详情 |
| **M2** | 功能账：任务即功能 + 缺陷按 `relatedFiles` 归属 + 未归属单列 + 手工指派 | 真实仓库"每功能待修数"与手工核对账本一致；未归属数量正确；指派后可撤销且不改账本 |
| **M3** | 并行视图（已具备，补齐入口） | 会话树/目录/活否正确；同目录双活报撞车；缺服务时降级 |
| **M4** | 任务板接入：认领 + 写作用域 | 派活后显示"谁在做什么"；两个任务 scope 有交集 → 跨目录冲突预警 |
| **M5** | 编排：派活 / 催一下 / 待人工决定 | 点击后目标会话真的收到消息；"待人工决定"只来自结构化字段，不从自由文本推断 |
| **M6** | 外部源（dsh-todos / 验收结果）——按需 | 每加一个源必须有降级分支与单测 |

## 12. 风险

| 风险 | 对策 |
|---|---|
| 每个源一份格式依赖 | 适配器隔离 + 每源必备"读不到"分支与文案 |
| 路径前缀匹配可能误挂缺陷 | 未归属单列 + 界面标注"按路径推断" + 不做模糊匹配 |
| 面板信息过载 | 每区有行数上限与截断提示；不上图表 |
| 数字造假（历史上出现过：读错路径导致 blocking 恒为 0） | 禁止默认值兜底；每个字段的读取路径必须有针对真实样本的回归测试 |

## 13. 待定（需要产品决策）

1. **技能触发权限**：哪些 skill 允许自动跑、哪些必须人点（对应 superagent 的 Policy/Mandate）。这决定 M5 能自动到什么程度——但无论怎么定，**执行权始终在会话里的 agent**，插件只负责"建议 + 派活"。
2. **是否要求结构化回写**：若希望面板稳定地回答"现在在等谁"，各 skill/会话需要按约定写结构化状态（类似 superagent 的 Report 字段），否则只能显示"最近有没有动静"。这是唯一需要改写作习惯的地方。
