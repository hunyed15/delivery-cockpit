# 项目驾驶舱 · 功能设计

> 对象：非技术创始人 / 独立开发者，多项目、以 AI 为主要开发力
> 插件：`@hunyed15/project-cockpit`（DeepSeek Harness 插件）

## 1. 定位与边界

**一句话**：把项目真实状态收拢成一屏，让人一眼知道——**做到哪了、卡在哪、谁在干、下一步做什么用什么**。

它负责**接线与抄表**：把现成的发动机（DSH 的 agent loop）、现成的轮子（skills / MCP）、现成的底盘（会话、工具、worktree）连起来，把人需要知道的信息抄到仪表上。

| 车的部件 | 在本系统里是什么 | 归属 | 插件做什么 |
|---|---|---|---|
| **发动机** | LLM agent loop：理解目标、选工具、纠错、收尾 | 现成，DSH 内核 | **只接线**：不造，也不复制它的判断 |
| 底盘 | 会话、工具、worktree、存储 | 现成，DSH 内核 | 读 |
| 轮子 | skills / MCP：trellis、审核、todos、前端设计、测试、Playwright… | 现成，各自插件或项目 | **只登记"本项目用哪些"，不复制文件** |
| 变速箱 | 派活通道：下发目标级指令 / 两步发送 | 插件实现 | 传话 |
| 多轮驱动 | subagent：同一目标下的并行执行单元 | 现成，DSH 内核 | 看见 + 发目标 |
| **仪表盘 + 方向盘** | 本插件：显示状态、指出唯一动作、按一下派活 | 本插件 | 显示、指路、派活 |

### 1.1 唯一的红线：不复制判断

买现成的发动机装到车上，不叫"造发动机"。真正的风险不是我们写代码，而是**同一个决定出现了两个决策者**：

| 谁 | 决定什么 |
|---|---|
| 会话里的 agent（发动机） | **怎么干**：调哪个 skill、什么顺序、失败怎么重试、代码怎么写 |
| 插件（仪表盘 + 调度器） | **干什么、什么时候干、干完没有、该不该找人** |

判据三问——插件能不能自己做这个决定：

1. 需要看代码 / 看界面才能决定吗？→ **给 agent**
2. 做错了要不要重试或换方案？→ **给 agent**
3. 只是按规则从已知选项里挑一个？→ **可以归插件**

按这个标准：**「这一阶段可用哪几类能力」归插件（查表），「具体用哪一个、怎么用、用几轮」归 agent。**

闭环（驱动权始终在 agent）：

```
读状态 → 算出唯一下一步（含"用哪个能力"）→ 派给会话
  ↑                                            ↓
结果写回（账本 / 执行回执）←── agent 在会话里执行（自己选技能、改代码、跑验证）
```

## 2. 范围

**这是 DSH 插件，只管 DSH 内部，不接外部 agent。**

- **项目 = 工作区（workspace）**。每新建一个工作区，插件里就有一条项目信息——**哪怕是空目录**，也要以「未初始化」形态出现，并给出"初始化工作区"的下一步。
- 一个工作区可有多个会话（单线开发 1 个，多 agent 并行 N 个）；会话是执行单元，项目是归属单元。
- 不给空工作区编造进度：没数据就是没数据。

## 3. 用户要回答的五个问题

| # | 问题 | 界面 |
|---|---|---|
| 1 | 我有哪些项目、各自到哪了？ | 项目总览（= 工作区列表） |
| 2 | 这个项目是干嘛的？ | 项目名片 |
| 3 | 做到哪了、卡在哪？ | 生命周期 + 三本账 |
| 4 | 下一步做什么、该用哪个能力？ | 下一步（含阶段能力推荐） |
| 5 | 谁在干、会不会撞？ | 并行 |

## 4. 设计原则

1. **不生产数据，只归一与投射。** 功能来自 trellis 任务，缺陷来自审核账本，动作来自执行回执，会话来自宿主服务。
2. **视图层不认识数据源。** 视图只认事实类型，不认具体文件格式。
3. **不给"看起来合理"的数字。** 读不到显示 `—` 或「待确认」，绝不默认 0、不猜状态、不解析自由文本算进度。
4. **一步一个动作。** 主按钮只有一个；需要人决策的事交回对话。
5. **同屏口径一致。** 数据不可信时，chip、下一步、阶段门、表格一起降级。
6. **人话优先，技术细节折叠。** 默认给人看"哪个功能、多严重"；`文件:行` 收进"技术详情"。

## 5. 信息架构：两级

**第一级 · 项目总览（= 工作区列表）**

```
项目                 阶段        待修  在跑   更新于
claude-code-review   挑毛病       3    2     14:40
SuJinCRM             写代码       0    1     09:12
临时会话             未初始化      —    —      —
```

- 空目录/未初始化工作区**不隐藏**，点进去给"初始化工作区"。
- 一行只放能算的字段；算不出的显示 `—`。

**总览怎么刷：冷热分层 + 缓存**

| 温度 | 判据 | 打开总览时 |
|---|---|---|
| 热 | 有活跃会话（`cwd` 命中该工作区），或最近 24h 有任务/账本变更 | 同步读，实时 |
| 温 | 7 天内变动过 | 先显示缓存，后台刷新 |
| 冷 | 超过 7 天没变动 | 显示缓存 + 「上次读取于 X」灰字；**点进详情才真正读** |

- **冷项目不隐藏**：始终在列表里，只是标注"数据可能过时"。隐藏会重演"看不见"的老问题。
- 缓存放 **profile 级**（总览跨工作区，不能放项目内）；缓存不可用时退回"限制并发地全读"。
- 提供「全部刷新」，冷项目也能一键更新。
- 缓存值必须带时间：`待修 3（14:40）`——没有出处的数字不允许显示。

**第二级 · 单项目详情**（自上而下）

```
┌ 项目名片（可折叠）─────────────────────────────────────────────┐
│ 一句话定位 · 技术栈标签 · 核心模块 3-5 个 · 一键预览命令          │
├ 数据可信度 ───────────────────────────────────────────────────┤
│ 项目名 · [待修 3 / 无待修 / 待确认] · 更新于 · 刷新 · ← 返回      │
├ 异常横幅（仅在有数据问题时，可重试）────────────────────────────┤
├ 下一步 ───────────────────────────────────────────────────────┤
│ 动作名 + 指令原文（含推荐能力）+ 理由 + 阶段能力推荐             │
│                          [去对话发送] [复制指令] [复制摘要]       │
├ 生命周期 ─────────────────────────────────────────────────────┤
│ 初始化→想清楚→定规格→搭骨架→写代码→挑毛病→验效果→发出去         │
├ 三本账 ───────────────────────────────────────────────────────┤
│ 功能（= 任务）｜未归属缺陷                                       │
├ 并行 ─────────────────────────────────────────────────────────┤
│ N 个在跑 / 共 M 个会话 · 撞车预警                                │
└───────────────────────────────────────────────────────────────┘
```

## 6. 各区功能

### 6.1 项目名片（Project Brief）

解决"隔三天回来忘了这项目是干嘛的"。

| 字段 | 来源 | 缺失时 |
|---|---|---|
| 一句话定位（给谁用、解决什么） | `brief.tagline`（人工/AI 写一次） | 「未填写」+ 下一步建议"生成名片" |
| 技术栈标签 | **自动探测**：`package.json` / `Cargo.toml` / `go.mod` / `pubspec.yaml` / `app.json` 等 | 显示"—" |
| 平台类型 | 从技术栈推断（Web / 桌面 / 移动 / 小程序） | — |
| 核心模块 3–5 个 | `brief.modules[]`：每项名称 + 一句职责 | 「未填写」 |
| 一键预览 | 自动取 `package.json` 的 `scripts.dev/start/preview`，或 `brief.preview` | 无预览命令时不显示按钮 |

- 文件：`.dsh/plugin-state/project.json`（trellis 不托管，插件只读）
- **自动探测优先**：技术栈与预览命令不要求人写，减少负担；只有"定位"和"模块职责"需要人/AI 写一次。

### 6.2 下一步

三层结构，缺一不可：

| 层 | 内容 |
|---|---|
| 动作名 | 人话（写需求文档 / 定接口契约 / 搭骨架 / 修问题 / 复检 / 验效果 / 发布 / 初始化） |
| 指令原文 | 可直接执行的文本，标识符等宽，**含本阶段推荐能力**（见 §8） |
| 理由 | 为什么是它（可反驳） |

状态机（优先级从上到下，覆盖全部阶段，见 §9）。

### 6.3 生命周期（八步）

| 步 | 名称 | 判据（证据） | 退出门禁（做完的标志） |
|---|---|---|---|
| 0 | **初始化工作区** | 存在 `.trellis/` **且** 存在 `.dsh/plugin-state/RULES.md` | 两者齐备（见 §7.4） |
| 1 | 想清楚 | `prd.md` 存在且非模板 | 需求确认（人看） |
| 2 | 定规格 | 存在设计/契约定稿（如 `docs/specs/*`、接口契约文件） | 契约冻结 |
| 3 | 搭骨架 | 存在可运行入口（如 `scripts.dev` / `main.*`） | 本地能启动空壳 |
| 4 | 写代码 | 存在 `in_progress` / `completed` 任务 | 功能任务完成 |
| 5 | 挑毛病 | 有审核轮次 **且无未处置 blocking** | 账本干净 |
| 6 | **验效果** | 验收表条目全部有结果 **且** 有截图/记录 | 核心路径真实跑通 |
| 7 | 发出去 | 有发布记录（版本号/链接/构建产物） | 可访问版本 |

- 展示为一条进度线 + 当前步一句话 + 依据；明细默认收起。
- 每步必须有 `basis`；推断出来的东西不装成事实。
- 第 0 步是**前置准备**，不计入"七步"，但必须在最前面——之前把"想清楚/定规格"排在"搭骨架"前却用 spec 文件当判据，逻辑是倒的。

### 6.4 三本账

**功能账**（= trellis 任务）

| 列 | 来源 |
|---|---|
| 功能名 | `task.title` |
| 状态 | `task.status` → 进行中 / 已完成 / 未开始 |
| 作用域 | `task.relatedFiles`（缺失 `—`） |
| 待修 | 归属到该功能的未处置 blocking 数 |
| 最近轮次 | 该功能账本最后轮次 + verdict |

**缺陷账**（人话优先）

- 默认展示：**严重度 + 标题 + 所属功能**；`文件:行` 收进「技术详情」折叠区。
- 归属：`issue.file` 按路径前缀匹配 `task.relatedFiles`；匹配不上进「未归属」。
- 未归属的处理顺序：
  1. 主按钮 **「让 AI 归类」**——两步发送一条指令，让 agent 读完代码后把归属写进 `.dsh/plugin-state/assignments.json`；
  2. 兜底：手工指派（写同一个文件，可撤销，界面上标「人工指派」）。
- **不生成账本里没有的信息**：没有"用户会遇到的现象"这个字段就不显示，需要解释时走「让 AI 说明」动作。

**门禁账**

- 最近一次 gate 结果 + 快照一致性；截断的 full pass 不算通过。

### 6.5 并行

| 列 | 来源 |
|---|---|
| 会话 | `sessionQuery.readTitleSnapshots`；子代理标层级 |
| 目录 | `SessionHeader.cwd` 与项目根比对 → 主工作区 / 其他目录 |
| 状态 | `ctx.sessions.list()`（内存态最权威） |
| 创建于 | `SessionHeader.createdAt` |

- 范围：`cwd` 在项目根下，或父会话在项目根下（worktree 会话属后者）。
- 撞车预警：两个"运行中"会话在同一目录 → 横幅点名。
- 不跑 git 判定 worktree，界面说"其他目录"。
- 上限 20 行，超出提示。

## 7. 数据事实与来源

**两类源**，这是控制复杂度的关键：

### 7.1 内建源（已存在、格式固定，直接读）

| 事实 | 来源 | 关键字段 |
|---|---|---|
| feature | `.trellis/tasks/*/task.json` | `title / status / subtasks / relatedFiles` |
| defect | `<task>/review/review-N.json`、`dispositions.jsonl` | `review.issues[].severity/file/line/key/issue`、`meta.failOn / meta.round` |
| session | `sessionQuery` + `ctx.sessions` | `header.cwd / parentSession / origin / delegationDepth / createdAt` |
| brief | `.dsh/plugin-state/project.json` + 技术栈探测 | `tagline / modules / preview` |

### 7.2 协议源（执行回执）

**回执是什么**：就像银行办完事给的那张小票——办了什么事、结果如何、几号窗口。任何 skill / MCP 跑完后，agent 往一个日志文件**追加一行**，记录：哪个阶段、用了什么能力、结果如何、一句人话、产物在哪、要不要人拍板。

**为什么需要它**：Playwright 输出截图、审核输出 JSON、脚手架输出日志——格式各不相同。**不为每个工具写解析器**，而是让它们都交一张同格式的回执，插件只读这一种记录。将来接任何社区能力都不用改插件。

改为定义一个极简协议：任何技能跑完，往 `.dsh/plugin-state/receipts.jsonl` 追加**一行**：

```json
{"at":"2026-11-20T14:40:12+08:00","stage":"验效果","skill":"playwright","status":"ready",
 "summary_for_human":"下单主流程跑通，下单页截图 2 张","artifacts":["shots/order-1.png"],
 "blocking_issues":[],"needs_human_decision":false}
```

| 字段 | 必填 | 含义 |
|---|---|---|
| `at` | ✅ | 时间 |
| `stage` | ✅ | 属于哪一步（想清楚…发出去） |
| `skill` | ✅ | 用了什么能力（自由字符串） |
| `status` | ✅ | `progress` / `waiting` / `ready` / `blocked` / `failed` / `dropped` |
| `summary_for_human` | ✅ | **一句人话**：发生了什么、人需要知道什么 |
| `artifacts` | — | 产物路径（截图、报告、构建物） |
| `blocking_issues` | — | 阻塞项（自由文本数组） |
| `needs_human_decision` | — | **结构化**声明"要人拍板" |

规则：

- 插件只维护 **1 个** 回执适配器，通吃未来任何社区能力。
- 「待人工决定」**只能**来自 `needs_human_decision: true`；**永不**从自由文本推断（这点照抄 `dsh-superagent` 的明确拒绝项）。
- 回执是**追加写**，永不修改历史；插件只读。
- 谁写：agent 在执行完技能后写。落法是给主会话一条全局规则（或一个"收尾"技能）。
- 插件须显示**"最近回执时间"**：太久没回执 → 提示"这个阶段可能没人在推"，但**不猜测**。

结构与 `dsh-superagent` 的 Report 状态一致（`progress / waiting / ready / blocked / failed / dropped` + Attention），已验证是好设计。

### 7.3 验收表（结构化 JSON）

文件 `.dsh/plugin-state/acceptance.json`（人/AI 写条目，AI 只能填结果）：

```json
{
  "version": 1,
  "items": [
    { "id": "a1", "title": "下单主流程",
      "steps": ["打开首页", "加入购物车", "提交订单"],
      "expected": "看到订单成功页",
      "result": null, "evidence": [], "at": null },
    { "id": "a2", "title": "空购物车下单",
      "steps": ["直接点提交"], "expected": "提示购物车为空",
      "result": "pass", "evidence": ["shots/empty-cart.png"], "at": "2026-11-20T14:40:12+08:00" }
  ]
}
```

| 字段 | 谁写 | 规则 |
|---|---|---|
| `id` / `title` / `steps` / `expected` | 人（或 AI 起草后人确认） | 「操作 → 应看到什么」必须是人话 |
| `result` | AI 执行后填 | `null` / `pass` / `fail` / `blocked`；**`null` 永远不等于 pass** |
| `evidence` | AI 填 | 截图/录屏/日志路径；`pass` 必须至少 1 个证据 |
| `at` | AI 填 | 执行时间 |

「验效果」这一步完成的判据：**所有条目 `result` 非 null 且 `pass` 的都有 evidence**。缺一条就还是未完成——不允许自评通过。

### 7.4 初始化工作区（释放规则与模板）

「初始化工作区」是一次**显式、幂等、可预览**的动作——类似 `trellis init`，用户点了才写。

**写入位置与内容**

```
<项目根>/.dsh/plugin-state/
  RULES.md            # 协作规则：回执义务、写作用域、自动驾驶边界（本次初始化生成）
  project.json        # 项目名片骨架（技术栈由插件自动探测后填入）
  playbook.json       # 阶段能力路由（由内置默认表生成，可改）
  acceptance.json     # 验收表骨架（空条目）
  receipts.jsonl      # 执行回执（运行时追加，初始化时不创建空文件）
```

**三类东西，处理方式不同**

| 类型 | 处理 | 原因 |
|---|---|---|
| 规则文档、配置模板 | ✅ 释放到项目目录 | 规则随项目走：换机器/换会话/换人都生效，可 git diff 审阅 |
| **技能本体（`SKILL.md`）** | ❌ **不复制** | 复制会变成两套副本，上游一更新就漂移。只在 `playbook.json` 里**登记名字**：本项目用哪些能力 |
| `AGENTS.md` 指针 | ⚠️ **不自动改**，给一行可复制文本 | trellis 托管 `AGENTS.md` 的部分区块，自动改容易和它的模板机制打架 |

`AGENTS.md` 建议粘贴的一行（放在 TRELLIS 区块之外）：

```
本项目使用项目驾驶舱插件：流程与规则见 .dsh/plugin-state/RULES.md（含"跑完任何技能必须追加一行执行回执"）。
```

**三条硬性约束**

1. **只在显式操作时执行**，不自动触发；
2. **幂等 + 不覆盖**：已存在的文件跳过；要覆盖必须先 `dry-run` 列出将写/将跳过的文件，由人确认；
3. **不碰 trellis 托管范围**：不写 `.dsh/DSH.md`、`.dsh/skills/*`、`AGENTS.md` 的 TRELLIS 区块（这三处由 `.trellis/.template-hashes.json` 管）。

**git 策略**

| 文件 | 是否提交 | 理由 |
|---|---|---|
| `RULES.md` / `project.json` / `playbook.json` / `acceptance.json` | **提交** | 团队共享、可 diff 审阅、换机即用 |
| `receipts.jsonl` | **忽略** | 本机运行日志：体积会涨、内容含本机路径 |

> 与 `AGENTS.md` 同理：初始化**不自动改 `.gitignore`**，而是给出可复制的一行 `.dsh/plugin-state/receipts.jsonl`。

## 8. 阶段能力路由（Playbook）

解决"每个阶段该用哪个社区 Skill / MCP"。**插件只推荐，不执行。**

- 文件：`.dsh/plugin-state/playbook.json`（可缺省，缺省用内置默认表）
- 结构：按**项目类型**（`web` / `desktop` / `mobile` / `miniapp` / `cli`）分，每阶段给 `skills[]` + `promptTemplate`

```json
{
  "type": "web",
  "stages": {
    "想清楚": { "skills": ["brainstorming"], "promptTemplate": "用 {skills} 把需求收敛成 prd.md：目标用户、核心流程、不做什么" },
    "定规格": { "skills": ["ux-design", "api-contract"], "promptTemplate": "用 {skills} 产出页面线框与接口契约，落到 docs/specs/" },
    "搭骨架": { "skills": ["scaffold"], "promptTemplate": "用 {skills} 初始化可运行空壳，并启动一次确认" },
    "写代码": { "skills": ["trellis"], "promptTemplate": "按任务逐个实现，任务状态流转到 completed" },
    "挑毛病": { "skills": ["claude_review"], "promptTemplate": "跑 claude_review(mode:\"gate\")，修完未处置 blocking" },
    "验效果": { "skills": ["playwright"], "promptTemplate": "按验收表跑核心路径，截图归档，写一条执行回执" },
    "发出去": { "skills": ["build"], "promptTemplate": "构建生产包，记录版本号与可访问链接" }
  }
}
```

默认表（内置，仅给**能力类型**；具体 skill 名由项目配置）：

| 阶段 | 人话要确认的事 | 能力类型 | 退出门禁（证据/产物） |
|---|---|---|---|
| 想清楚 | 做什么、不做什么 | 需求收敛/PRD | `prd.md` |
| 定规格 | 长什么样、数据怎么走 | UI/UX 设计、接口契约 | 线框 + 契约文档 |
| 搭骨架 | 技术栈对不对、空壳能跑吗 | 脚手架 | 能启动的空白页 + 名片 |
| 写代码 | 功能逐个实现 | 任务拆解与执行 | 任务 completed |
| 挑毛病 | 有隐患吗、合规吗 | 代码/视觉/安全评审 | 账本无未处置 blocking |
| 验效果 | 真实点一遍能用吗 | 浏览器自动化 / 移动端测试 | 验收表全绿 + 截图 |
| 发出去 | 能上线吗 | 构建部署 | 版本号 / 链接 |

「下一步」的指令原文由 **当前阶段 + Playbook** 组装，例如：

> 用 `playwright` 按验收表跑「下单主流程」，通过后截图存 `shots/`，并写一条执行回执（stage=验效果, status=ready）。

## 9. 下一步状态机（覆盖全部阶段）

| 优先级 | 条件 | 动作 | 指令要点 |
|---|---|---|---|
| 1 | 无 `.trellis` | 初始化工作区 | 初始化 trellis 并建第一个任务 |
| 2 | 无 `prd.md` | 写需求文档 | 按 Playbook「想清楚」组装 |
| 3 | 有 prd、无契约定稿 | 定规格 | 按 Playbook「定规格」 |
| 4 | 有契约、无可运行入口 | 搭骨架 | 按 Playbook「搭骨架」 |
| 5 | 有未处置 blocking | 修问题并复检 | 列出那几条 + gate |
| 6 | 有已 fixed 待复检 | 复检本轮修复 | `mode:"range"` |
| 7 | 从未审核 | 第一次审核 | `mode:"full"` |
| 8 | 审核干净、验收表未跑/未全绿 | **验效果** | Playbook「验效果」 |
| 9 | 验收通过、无发布记录 | 发出去 | 构建 + 记录版本 |
| 10 | 全部完成 | 跑提交门禁 | `mode:"gate"` |

任何一步的数据不可信 → 降到「先确认数据」并禁用主按钮。

## 10. 自动驾驶模式

叫"驾驶舱"就该能自动驾驶。但"自动驾驶"要分清**谁拥有循环**——这决定它是能力还是坑。

### 10.1 三档

| 档 | 谁点开始 | 谁决定调什么技能 | 人何时介入 | 适用 |
|---|---|---|---|---|
| **L0 手动** | 人点「去对话发送」 | agent | 每步 | 今天就有 |
| **L1 半自动**（默认推荐） | 人点一次「开始这一阶段」 | **agent 自主决定**，按 Playbook 能力清单自己选 | 只在 `needs_human_decision=true`、预算耗尽、连续失败时 | 日常 |
| **L2 全自动** | 无（定时/事件触发） | agent | 只看「待人工决定」列表 | 成熟项目、夜间跑 |

**关键**：L1/L2 里插件给的是**候选清单**，不是"指令"。它把「阶段 + 目标 + 可用能力 + 完成标准 + 边界」打包下发；**agent 可以挑清单里的、也可以不用、也可以自己找别的**——决定权和重试权都在 agent。

这就是"AI 自己决定调用什么 skill 就自动跑"：**插件查表报菜名，agent 点菜和做菜。**

### 10.2 自动驾驶指令长什么样

插件生成的目标级指令包含五段（缺一不可）：

```
【阶段】验效果
【目标】让「下单主流程」在真实浏览器里跑通
【可用能力】playwright、chrome-devtools（来自 Playbook，agent 可自行取舍）
【完成标准】验收表 3 条全部有结果 + 至少 2 张截图 + 写一条执行回执（status=ready）
【边界】只读代码；不改 .trellis 结构；不 push；最多 20 轮；卡住就停下来问人
```

agent 拿到它之后自己做计划、自己调技能、自己重试。插件**不参与**中间决策。

### 10.3 护栏：分清"谁强制"

**强制边界不归插件。** 能不能 push、能不能删文件、能不能改账本，由 **DSH 会话自身的沙箱策略与工具审批**（会话 / 预设层）决定；插件既不拥有这个权力，也不复制这套判断。插件在指令里写"边界"，只是**提示**，不是强制。

| 边界 | 谁强制 | 插件做什么 |
|---|---|---|
| push / 删文件 / 改账本 / 访问网络 | **DSH 沙箱策略 + 工具审批**（会话层） | 指令里提示一句；权限本身不碰 |
| 这一阶段允许用哪些能力 | 插件（Playbook 候选清单）+ agent 取舍 | 给出候选，让 agent 挑 |
| 预算：轮数 / 时间 / 成本 | 写进指令，执行中由 agent 自律 | 超限后展示"已停下，需要人" |
| 停止条件 | agent 按指令停；插件读回执发现异常 | 把"需要人"的挑出来 |
| 回执义务 | 项目规则（事前）+ 插件检测（事后） | 显示"本阶段有动作但无回执" |
| 可追溯 | 插件留存每次下发的指令原文 | 面板可查"当时我是怎么让它干的" |

### 10.4 技术上怎么落地（如实标注）

| 路径 | 状态 |
|---|---|
| **A. 两步发送**：面板生成自动驾驶指令 → 人点一次发送 → agent 自主跑 | **今天就能做**（通道已验证） |
| **B. 插件直接起子代理**：Host 用 `ctx.subagents.startActivation(...)` 派活，无需人点 | **需探针验证**：服务方法确认存在，但"插件在没有活跃 agent 上下文时能否启动、结果如何回流"未验证 |

L2 全自动依赖路径 B；L1 用路径 A 即可。**没有验证过的路径不写进承诺**，先做 A，B 作为 M 级任务单独探针。

### 10.5 插件在自动驾驶里的职责

只做三件事：**下发目标**、**观察回执**、**把"需要人"的挑出来**。

不做三件事：**不实现循环、不重试、不替 agent 选技能**。按 §1.1 的三问判据，这三件都属于"需要看代码/看界面、做错要换方案"的决定——归 agent。

## 11. 架构分层

```
内建适配器   trellis 任务 · 审核账本 · sessions · 项目名片
协议适配器   执行回执 receipts.jsonl（1 个，通吃所有社区能力）
   ↓ 只读、可选、互不依赖；一个源坏了只影响它自己
归一化层     事实：feature / defect / gate / session / brief / receipt
   ↓ 纯函数、可单测
视图层       名片 · 下一步 · 生命周期 · 三本账 · 并行 · 可信度
   ↓
行动层       唯一下一步 → 下发（Agent Teams 派活 / 两步发送）
```

**硬约束**：视图层不得 import 任何适配器；新增数据源只允许新增适配器（优先用回执协议而不是新写格式解析）。

### 11.1 派活底座：Agent Teams（点名，不另造）

多 agent 的"派活 / 谁在做什么 / 写作用域冲突"**不再自己设计协议**，直接站在 DSH 的 Agent Teams 上：

| 现成能力 | 插件怎么用 |
|---|---|
| `team_task_create` / `team_task_update`（认领、`write_scopes`、`blocked_by`、CAS 更新） | 作为**任务与认领的权威记录**；插件只读，不自己存一份 |
| `subagents`（启动 / 名单 / 层级） | 并行执行单元；插件只"看见"与"发目标"，不负责启停 |
| Agent Teams 的 `owner`（agent 名） | 用来把"会话 ↔ 任务"对上，从而回答"谁在做什么" |

因此插件**不引入新协议**：认领用任务板、派活用 subagent、冲突用 `write_scopes` 交集判断。缺了 Agent Teams 时（例如 profile 未启用）分区显示原因并降级，不伪造。

## 13. 非目标

- 不重造待办、不做甘特图/趋势图/热力图
- 不写项目源码；自有状态只写 `.dsh/plugin-state/`（trellis 不托管）
- 不解析 PRD 自由文本算完成度、不跑 git 判定 worktree、不猜"在等人"
- 不替 agent 选技能、不重试、不编排执行顺序（判据见 §1.1）
- 不做多项目并联计算以外的跨项目联动

## 14. 里程碑与验收

| 步 | 内容 | 验收标准 |
|---|---|---|
| **M0**（已具备） | 下一步（基础分支）/ 可信度三态 / 生命周期 / 缺陷计数 / 并行 / 提醒 / 摘要 | 现有 437 条断言全绿；真机路由与插槽正常 |
| **M1** | **初始化工作区**（释放规则与模板，幂等 + dry-run）+ 项目名片（自动探测 + 手填两字段）+ 项目总览（工作区列表，空目录可见，冷热分层 + profile 级缓存） | 点一次初始化后 `.dsh/plugin-state/` 出现四个文件且二次执行不覆盖；新建空工作区出现「未初始化」行；名片技术栈与预览命令无需手写即可显示 |
| **M2** | 执行回执协议 + 1 个协议适配器 + "最近回执时间" | 手工追加一行回执 → 面板出现该事件；无回执时显示"该步无记录"而非猜测 |
| **M3** | Playbook + 下一步状态机补全（10 条分支） | 每个阶段点开都能得到"该用哪个能力"的指令原文；缺 Playbook 时用默认表 |
| **M4** | 验效果 v1：验收表 JSON + 结果/证据记录 + 截图归档 | 每条有「操作/期望」；`null` 不等于 pass；`pass` 必须有 evidence；未跑完时下一步就是「验效果」 |
| **M5** | 自动驾驶 L1：下发目标级指令（阶段+目标+能力+完成标准+边界），人点一次即可自主跑 | 点一次能连续完成多个技能动作并写出多条回执；遇到 `needs_human_decision` 会停下等人 |
| **M6** | 功能账人话化 + AI 自动归类（手工指派兜底） | 缺陷默认不露 `文件:行`；AI 归类写入 assignments.json 后可撤销 |
| **M7** | 任务板接入 + 并行防撞 + 派活 | 认领后可看到"谁在做什么"；scope 有交集 → 预警 |
| **M8** | 自动驾驶 L2：`ctx.subagents.startActivation` 免人手启动 | 实现首日先用真实 API 跑通一次（约 10 分钟）；跑不通就退回 L1 并说明原因，不硬凑 |
| **M9** | 外部源（如 dsh-todos）按需 | 每加一源必须有降级分支与单测 |

排序理由：先把"看懂项目 + 知道该用什么能力 + 真实跑一遍"做通（M1–M4），再做人话化与并行协同。

## 15. 风险

| 风险 | 对策 |
|---|---|
| 回执没人写 | 插件显示"最近回执时间"；把写回执做成收尾技能；缺回执只降级不猜 |
| Playbook 配了不存在的 skill | 只显示名字与指令，不假设它存在；执行失败由 agent 汇报 |
| 技术栈探测误判 | 标签标「探测」，可被 `project.json` 覆盖 |
| 验收表变成形式主义 | 必须有截图/记录作为证据，否则该步不算完成 |
| 数字造假（历史教训：读错路径导致 blocking 恒 0） | 禁止默认值兜底；每个字段读取路径要有真实样本回归测试 |

## 16. 待定

1. **冷/热分界**：暂定 7 天，是否需要按项目活跃度自适应？
2. **缓存失效策略**：profile 级缓存在 DSH 重启后保留多久（放文件持久化 vs 仅内存）。
3. **L2 落地细节**：`ctx.subagents.startActivation` 的调用上下文与结果回流方式，实现首日跑通一次再定稿（成本约 10 分钟，失败就退回 L1 并说明原因）。
