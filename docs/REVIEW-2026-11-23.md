## 3. 真实使用冲突（按场景）

### U1 旧项目升级：所有历史项目突然被要求签核/补文件（重要）

真实证据读取总会附带 `approval.decisions`（缺文件时四门全 false），所以新插件的 4.2/4.6/12.2/12.8 决策门**对所有项目生效**，没有"老项目豁免/迁移"路径。

探针：一个已有 `release` 完成回执、已有 PRD 的旧项目 → 下一步变成 **4.2 范围签核**，而不是开下一轮。要恢复必须从范围/架构/验收逐门补签。

### U2 已发布项目被要求补发布清单，无法直接开下一轮（重要）

探针：旧项目已有 `release` 回执、验收 pass、四门签核，但没有 `.dsh/plugin-state/release.json` → 状态机 12.5 先返回 **"准备发布清单"**（`lib/state.js:293-297`），而不是 14 "开启下一轮"。已发布事实被发布清单门挡住。

### U3 空任务列表会让"已发布"项目卡在"先拆任务"（重要）

探针：`.trellis` 存在但 `tasks` 为空、迭代已发布 → 优先级 7 返回 **"先拆任务"**，永远到不了发布/下一轮。Trellis 任务归档后就会出现。

### U4 Trellis 接入是"半接入"（重要）

`cockpit_init` 只创建一个空 `.trellis/` 目录（`lib/init.js:91-95`），而全局安装的 `trellis-start/brainstorm/check/...` 明确要求 `./.trellis/scripts/get_context.py`。playbook 又把 `trellis-brainstorm` / `trellis-finish-work` 写成阶段 method。结果：
- 面板显示这些能力"可用"（技能确实装了），但项目里直接调用会失败；
- 用户必须额外跑一次 `trellis init`，这件事文档/初始化都没有提示或自动完成。

### U5 小改动也走重流程（中）

9 阶段迭代环每个迭代固定要 4 个人工门（范围/架构/验收/发布）+ 架构契约文件 + 测试报告 + 发布清单。修一个文案/小 bug 时没有"轻量变更"路径（playbook 覆盖又会被版本规则整段忽略，见 D9），实际使用会倾向于"绕过流程"。

### U6 MCP/能力"可用"与"真的可用"混淆（中）

- `readMcpNames` 只把 manager 列表/工具名当存在性（注释明确"不混连接状态"）：manager 配置了但连接失败/重连中的 server 仍显示可用，指令会下发注定失败的操作。
- 本机直连 client 的 Playwright/Context7 已修复为能从 `mcp__<server>__` 工具名识别，但同样不反映连接失败。
- Playwright MCP 可以导航任意 URL（包括内网），而插件自带截图引擎强制回环；两套浏览器能力的边界不一致。

### U7 团队泳道只看精确 cwd（中）

`lib/team.js:117` 用 `samePath(header.cwd, targetPath)` 精确匹配：worktree/子目录里运行的子代理不会显示；只显示 live 会话，历史子代理只能靠回执。与"看子代理在干什么"的预期有偏差。

### U8 周报 days 参数语义半生效（低）

`/report?days=14` 只改标题日期范围；指标仍是"近 7 天发布 / 近 30 天返工率"（`lib/report.js` 已文档说明），但用户容易理解为"14 天窗口"。

### U9 DORA 指标是本地代理（低，已文档化）

返工率=review verdict 比例、修复时长=review→fixed 处置中位；不是线上变更失败率/MTTR。接线上监控前不能对外宣称真实 DORA。
